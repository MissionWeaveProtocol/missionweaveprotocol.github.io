# 準拠とアップグレード

適合性は、ブランチ名や SDK が MissionWeaveProtocol をサポートするという一般的な主張ではなく、正確な成果物セットに属します。ローカルの
[標準リリース ID](../../../reference/normative-release/)
から始めて、固定されたすべてのダイジェストを検証してから、該当する証拠サーフェスを実行します。

## 必要な証拠レイヤー

1. [JSON スキーマ カタログ](../../../reference/schemas/)
   は正確なスキーマ カタログを定義します。耐久性のあるオブジェクトの形状とアサートされた形式。
2. [構造適合バンドル](../../../reference/conformance/structural/)は、期待される有効なプロトコル文書と期待される無効なプロトコル文書を実行します。
3. [暗号バンドル](../../../reference/conformance/cryptography/)
   6 つのセマンティック ステージを通じてすべての Signed
   Document プロファイルを実行します。
4. [アドミッションバンドル](../../../reference/conformance/admission/)は、固定された暗号バンドルの上で初回アドミッションと履歴信頼を検証します。
5. 完全なランタイムの主張には、さらに肯定的および否定的な証拠が必要です。コマンド、イベント、状態遷移、リプレイ、フェンシング、認可、予算、障害回復、および古いまたは重複した副作用。

ローカル [適合概要](../../../reference/conformance/)
はこれらのサーフェスを分離するため、あるレイヤーを通過しても別のレイヤーに暗黙的に昇格されることはありません。

## ケースの前にマニフェストを検証する

暗号化バンドルの場合、フィクスチャ スキーマを検証し、最上位の `artifactDigest`
メンバーを正確に削除し、残りのマニフェストを JCS で正規化し、SHA-256 でハッシュし、ケースを実行する前に宣言されたすべてのアーティファクト バイト ハッシュを検証します。 ([MWP-EXT-011](../../../reference/specification/errors-extensions-and-security/#mwp-ext-011))。

アドミッションマニフェストは同じダイジェスト手順を使用し、変更されていない暗号ダイジェストをさらに固定します。アダプターの結果を実行する前に、参照されているすべてのアーティファクトとそのピンを確認してください ([MWP-EXT-012](../../../reference/specification/errors-extensions-and-security/#mwp-ext-012))。

## 証明されたサブセットを述べます

スキーマ ベクトルは、スキーマとベクトルの動作を証明します。暗号化は 6 つの検証段階を証明します。アドミッションはさらに、宣言された初回アドミッションおよび履歴リプレイのケースを証明しますが、Command の鮮度、署名者の認可、ステートマシンの受け入れ、またはデプロイ済み Admission
Log のポータブルな証明形式は証明しません。リファレンス実装は、自動化された肯定的証拠と否定的証拠がすべてのコア Command 種類、すべてのコア Event 種類、およびすべての遷移行をカバーする場合にのみ、完全な MissionWeaveProtocol
0.1 準拠を主張できます。それ以外の場合は、より狭い検証済みサブセットを明示的に報告します ([MWP-EXT-013](../../../reference/specification/errors-extensions-and-security/#mwp-ext-013))。

## 拡張機能と互換性

Extension
Profile は、グローバルに一意な URI、セマンティック バージョン、スキーマ URI とハッシュ、機能、重要度、および Organization 承認署名 ([MWP-EXT-001](../../../reference/specification/errors-extensions-and-security/#mwp-ext-001)) を宣言します。不明な非クリティカル拡張データは保持および中継できますが、不明なクリティカル プロファイルに依存する移行は拒否されます ([MWP-EXT-002](../../../reference/specification/errors-extensions-and-security/#mwp-ext-002))。どのプロファイルも、アイデンティティ、順序付け、冪等性、フェンシング、予算、Approval、来歴、分離、または Message/非権限不変式 ([MWP-EXT-003](../../../reference/specification/errors-extensions-and-security/#mwp-ext-003)) を弱めることはできません。

v0.1 スキーマは、不明なコア プロパティを拒否し、明示的な拡張メンバーを通じてのみ拡張性を認めます。可能であれば、正規リレー用に未知の非クリティカル拡張バイトを保存します ([MWP-EXT-010](../../../reference/specification/errors-extensions-and-security/#mwp-ext-010))。

割り当てピン Agent
Card と必要な機能のバージョン。互換性のない機能アップグレードはアクティブな作業をチェックポイントし、実行を続行する前に再度承認する必要があります ([MWP-IDN-003](../../../reference/specification/identity-registry-and-sessions/#mwp-idn-003))。

## アップグレードルール

下位互換性の仕様を明確にするために、ワイヤ `protocolVersion` は `0.1`
のままです。コア セマンティクス、必須フィールド、または署名バイトを変更するには、ネゴシエートされた新しいワイヤ マイナー バージョンまたはメジャー バージョンが必要です。新しい署名エンベロープ保護ルールをサイレント v0.1 の動作として導入しないでください ([MWP-SDV-019](../../../reference/specification/signed-documents-and-trust/#mwp-sdv-019))。

:::note[Implementation note]

アップグレードを新しい不変のリリース セットとして扱います。新しい Web サイトのリリース、スキーマ、マニフェスト、SDK ピン、生成されたインベントリを一緒にステージングします。隔離された環境で検証します。その後、双方が必要なワイヤ バージョンと拡張プロファイルをサポートする場合にのみ、トラフィックをネゴシエートまたはロールします。

古いバリデータと履歴 Registry/許可証拠を、正確なリリースに基づいて作成された記録を再生できるように保管してください。カナリア処理、ロールバック ウィンドウ、データベース移行ツール、およびデプロイメント シーケンスは運用上の選択肢ですが、ロールバックでは、すでに受け入れられた署名バイトやイベントを再解釈することはできません。

:::
