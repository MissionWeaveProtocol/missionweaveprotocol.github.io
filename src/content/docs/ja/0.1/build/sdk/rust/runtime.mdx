# Rust ランタイムリファレンス

このページでは、[正確な API 在庫](../api/)] で表される完全なクレート ルート サーフェスをカバーします。共有プロトコルの動作は、ローカルの
[ランタイム参照 ](../../../runtime/architecture-and-bootstrap/) および
[参照句 ](../../../../reference/specification/)] によって定義されたままです。以下のモジュール名は実装の由来を示しています。モジュール自体はプライベートであるため、呼び出し元は
`missionweaveprotocol` からパブリックな再エクスポートをインポートします。

<SupportStatus status="implemented" /> は、以下にリストされているクレートルート
API とプロセス内動作に適用されます。

<SupportStatus status="deployment-adapter-required" /> は、現在の Registry
権限、信頼されたアドミッション コンテキスト、認証されたログ
アクセス、およびその他のデプロイメント サービスに適用されます。

<SupportStatus status="not-implemented" />
は、正確に固定されたクレートに対応するランタイムがないことを意味します。

## クレートと実行モデル

クレートのバージョンは `0.1.0`
で、エディション 2024 を使用し、サポートされる最小ツールチェーンとして Rust
1.85 を宣言し、1 つのバイナリ `missionweaveprotocol-conformance` を公開します。
`src/lib.rs`
は唯一のパブリック インポート ルートです。内部モジュール パスはサポートされている API ではありません。

クレートをインストールしても、サービスは開始されず、ソケットも開かず、状態も保持されず、権限も付与されません。返されたバイト スライスと証拠オブジェクトは、アプリケーションが意図的に保存または送信しない限り、ローカル プロセス値のままです。

## 検証、署名、および Registry の証拠

`SchemaCatalog::new`、`validate`、`validate_bytes`、および `identifier`
は、22 個の正確な埋め込みスキーマ上で動作します。厳密な解析とスキーマ検証は正規化とは別のものです。
`canonical_bytes`、`canonical_sha256`、および `signature_input` は、RFC
8785 と署名入力構造を実装します。

`SigningKey` は、アプリケーション所有の署名シームです。 `Ed25519Signer`
は、ローカルでの使用を制御するためのシードベースの署名および検証ヘルパーを提供します。
`SignedDocumentCodec::sign` および `verify` は、9 つ​​の明示的な
`SignedDocumentKind`
値のいずれかを選択し、解析、スキーマ、署名エンベロープ、鍵解決、正規化、および署名の各ステージを順番に実行します。

`KeyResolver::resolve`
は、完全に保持された履歴を含む、1 つの一貫した該当する Organization リビジョンに対する
`KeyRegistrySnapshot::organization_wide`
証拠を返さなければなりません。選択されたキー、部分的な投影、キャッシュ ヒット、または呼び出し元が提供した信頼フラグが不十分です。
`VerifiedSignedDocument`
は、受信したバイト、署名、完全な正規のバイトとハッシュ、保護された時間、署名の証拠、および解決された Registry の証拠を公開します。

## フレーム、バンドル、および適合性

`FrameCodec::decode`、`encode`、および `validate_document`
はフレーム値を検証します。これらは、トランスポート、セッション認証、カーソル永続性、バックプレッシャー、ルーティング、または権限のある状態遷移を所有しません。

`ProtocolBundle::verify`
は、22 個のスキーマと 59 個のファイルの構造バンドルをチェックします。
`verify_cryptography`
は、98 個のアーティファクト、22 個のケース、および 62 個の宣言された評価をチェックします。
`verify_admission`
は、19 個のアーティファクト、5 個のケース、および 30 個の宣言された評価をチェックします。これら 2 つの呼び出しにより、ピン、カウント、ダイジェストが検証されます。すべての暗号化やアドミッション評価を実行するわけではありません。適合バイナリと
`ConformanceRunner::run` は構造ベクトルのみを実行します。

## 初回入場

`AdmissionService::new`、`prepare_first_admission`、`admit_first`、および
`verify_historical_admission` は、正確な入場フローを公開します。
[Rust アドミッション リファレンス ](../admission/)] に進み、アダプターの結果、呼び出し順序、および実行可能なパッケージ コンシューマーの例を確認します。

## 明示的な可用性境界

<SupportStatus status="deployment-adapter-required" /> **承認権限** -
アプリケーションは、現在の Registry 証拠、過去の Registry
証拠、信頼できる受け入れコンテキスト、および認証された追加専用ログを提供します。

<SupportStatus status="not-implemented" /> **Mission オーケストレーション** -
高レベルの Mission ステート マシンまたはオーケストレーション
ファサードはエクスポートされません。

<SupportStatus status="not-implemented" /> **Worker スケジューラ** - Worker
キュー、スケジューラ、リース ランナー、またはリカバリ
ループはエクスポートされません。

<SupportStatus status="not-implemented" /> **ホストされたゲートウェイ サービス**

クレートは、トランスポート、TLS、セッション、ルーティング、またはバックプレッシャーの所有権を備えたゲートウェイサービスではなく、フレーム コーデックを提供します。

<SupportStatus status="not-implemented" /> **権限のある永続性ランタイム** -
データベースベースまたは Agent
ローカルの永続性ランタイムはエクスポートされません。

これらの不在は、文書化されたサポート契約の一部です。 Python 参照ランタイム機能は、共有プロトコル名から推測してはなりません。
