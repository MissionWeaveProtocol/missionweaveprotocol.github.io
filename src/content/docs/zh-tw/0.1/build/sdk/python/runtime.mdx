## 導入模型

`missionweaveprotocol.__init__`
為簽署的文件、存取、捆綁驗證、預算、租賃和授權提供精心策劃的頂級匯出。更廣泛的參考運行時是公共子模組 API： 進口
`Core` 從 `missionweaveprotocol.core`, `AgentRuntime` 從
`missionweaveprotocol.agent`, `Scheduler` 從
`missionweaveprotocol.scheduler`，以及記錄在模組中的其他名稱 API 存貨。不要假設每個公共子模組類型都是從包根目錄重新匯出的。

## 核心、商店和交易邊界

`Core` 是權威的狀態機外觀。其公共 `query`、`replay` 和 `perform` 操作由
`AuthoritativeStore`
支援。商店合約揭露了交易、檢查和生命週期邊界；記憶體中、SQLite、通用 SQL 和 PostgreSQL 實作不會改變協議的原子性、修訂、冪等性或防護要求。

`SQLiteAgentStore`
是 Agent-本地。它儲存重播位置、Group 上下文、檢查點、調度程序狀態、已見事件和掛起的出站操作，以便 Agent 可以恢復。這些投影是可重建的，不能成為 Mission 或 Group 真相的權威。繼續使用[持久性和恢復](../../../runtime/persistence-and-recovery/)進行規範分離。

外部資料庫是部署相依性。 `PostgreSQLStore`
需要設定資料庫服務和驅動程式；連線可用性或本機快取命中並不能證明已提交權威轉換。

## Agent，調度程序與重播

`AgentRuntime.start_session` 建立單一活動本地會話並傳回
`AgentRuntimeSession`。此會話接受 Group 範圍的上下文和憑證、準備執行並公開
`Scheduler`。調度程序承認工作，應用轉換，調度或搶佔，並從快照重建。
`AgentReplay` 和 `EventProjector`
從有序事件恢復本地投影並拒絕間隙或不一致的投影狀態。

執行租賃、策略、預算和委託 API 是單獨的檢查。在產生副作用之前，計劃的項目仍然需要當前的防護、已接受的工作、適用的政策、剩餘預算和有效的最低權限授權。

## 驗證、信任和框架

在受保護的處理之前，請先驗證嚴格的 JSON 和固定的草案 2020-12 架構，保留協議標量字節，規範化簽名投影，驗證 Ed25519 材料，並從完整的 Registry 金鑰中解析。確切的六階段順序在[驗證、標準化和簽章](../../../runtime/validation-canonicalization-and-signing/)中指定。

`missionweaveprotocol.wire` 擁有類型化框架模型以及
`parse_frame`、`parse_received_frame` 和 `encode_frame`。 `GroupGateway`
將這些訊框綁定到會話啟動、訂閱、遊標、重播和核心操作。生產網路部署必須提供安全綁定、驗證輸入、TLS
1.3 憑證和金鑰、背壓限制和操作隔離。 Python 套件提供網關執行時間；它不提供部署網路權限。

## 一致性和升級

`SchemaCatalog` 和 `run_manifest` 執行支援的本地驗證表面。
`verify_cryptography_bundle` 和 `verify_admission_bundle`
將打包的工件綁定到記錄的引腳和摘要。 `missionweaveprotocol-conformance`
向操作員公開結構清單運作程序。在檢查打包的密碼學和准入工件身份時，分別呼叫兩個捆綁驗證函數。

每當 SDK 提交、協定 pin、架構集、加密套件、存取包或部署適配器發生變更時，請再次執行一致性。傳遞一個子集僅證明該子集；它不建立資料庫持久性、網路安全性、硬體容量或生產準備。
