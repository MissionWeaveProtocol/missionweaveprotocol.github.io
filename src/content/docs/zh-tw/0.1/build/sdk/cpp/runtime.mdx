## 库和执行模型

安装的包需要 C++20、CMake 3.24、OpenSSL 3 和 jsoncons
1.8.1。其导出目标为`MissionWeaveProtocol::sdk`；安装的公共标头位于
`include/missionweaveprotocol` 下。单独安装的可执行文件是
`missionweaveprotocol-conformance`。

链接库不会启动任何服务，不会打开套接字，不会创建持久存储，并且不会授予任何权限。

## 驗證、簽名和 Registry 證據

`parse_strict_json` 只接受一個 JSON 值。 `SchemaCatalog::validate`
檢查 22 個嵌入式草案 2020-12 架構。
`canonical_json`、`canonicalize_json`、`canonical_sha256` 和
`canonical_sha256_document` 實現 RFC 8785 表面。

`SigningKey` 是應用程式擁有的簽章介面。 `Ed25519`
公開嚴格的金鑰、簽章和文件幫助程序。 `SignedDocumentCodec::sign` 和 `verify`
選擇九個 `SignedDocumentKind`
值之一併執行解析、架構、簽章信封、金鑰解析、規範化和簽章階段。

`KeyResolver::resolve` 必須回傳 `KeyRegistrySnapshot::organization_wide`
證據，以取得具有完整保留歷史記錄的一個連貫的適用 Organization 修訂版。選定的金鑰、部分投影、快取命中或呼叫者提供的信任標誌是不夠的。
`VerifiedSignedDocument`
公開接收到的位元組、簽章和規範字串和雜湊值、受保護的時間、簽章資料以及解析的 Registry 金鑰和 Principal。

## 框架、捆綁包和一致性

`FrameCodec::decode`、`encode` 和 `validate_document`
驗證訊框值；它們不擁有傳輸、TLS、會話驗證、遊標持久性、路由、背壓或權威狀態轉換。

`ProtocolBundle::verify` 檢查 22 個架構和 59 個檔案結構套件。
`verify_cryptography` 檢查 98 個工件、22 個案例和 62 個聲明的評估；
`verify_admission`
檢查 19 個工件、5 個案例和 30 個聲明的評估。這些呼叫驗證引腳、計數、路徑、位元組長度和摘要，但不執行每個加密或存取評估。

`ConformanceRunner::run` 和 `missionweaveprotocol-conformance`
僅執行嵌入的結構模式向量。只有當所有向量都符合其預期有效性時，可執行檔才會傳回零。

## 首次入場

`AdmissionService` 公開 `prepare_first_admission`、`admit_first` 和
`verify_historical_admission`。繼續使用
[C++ 准入參考 ](../admission/)，以了解確切的適配器結果、呼叫順序和可運行的連結範例。

## 明確的可用性邊界

<SupportStatus status="deployment-adapter-required" /> **准入權威服務** —
應用程式提供當前 Registry 證據、歷史 Registry
證據、可信任接受上下文以及經過驗證的僅附加日誌。

<SupportStatus status="not-implemented" /> **Mission 編排** — 不匯出進階 Mission
狀態機或編排外觀。

<SupportStatus status="not-implemented" /> **Worker 排程器** — 不匯出 Worker
佇列、排程器、租用執行程式或復原循環。

<SupportStatus status="not-implemented" /> **託管閘道服務** — 庫提供
`FrameCodec`，而非具有傳輸、TLS、會話、路由或反壓所有權的閘道服務。

<SupportStatus status="not-implemented" /> **權威持久性運行時** —
不匯出資料庫支援或 Agent 本地持久性運行時。

這些未實作項目是書面支援合約的一部分；不得從共享協定名稱推斷 Python 參考執行階段能力。
