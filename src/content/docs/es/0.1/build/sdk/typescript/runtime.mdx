# TypeScript referencia de tiempo de ejecución

Esta página cubre la superficie TypeScript completa representada por el
[inventario API exacto](../api/). El comportamiento del protocolo compartido
permanece definido por la
[referencia de tiempo de ejecución ](../../../runtime/architecture-and-bootstrap/)
y las [cláusulas de referencia ](../../../../reference/specification/) locales.
Los nombres siguientes definen cómo el paquete anclado expone ese
comportamiento.

<SupportStatus status="implemented" /> se aplica a las API raíz del paquete y a
los códecs en proceso que se enumeran a continuación.

<SupportStatus status="deployment-adapter-required" /> se aplica a la autoridad
Registry actual, al contexto de admisión confiable, al acceso al registro
atómico autenticado y a otros servicios externos proporcionados por una
implementación.

<SupportStatus status="not-implemented" /> significa que el paquete fijado
exactamente no tiene un tiempo de ejecución público correspondiente.

## Modelo de importación y ejecución.

Importe nombres públicos de `@missionweaveprotocol/sdk`. El paquete publica
puntos de entrada ESM y CommonJS y requiere Node.js 20 o posterior. No expone
subrutas admitidas como `@missionweaveprotocol/sdk/admission`; Los nombres de
los módulos de origen que aparecen a continuación son agrupaciones de
procedencia para la raíz del paquete único API.

SDK utiliza criptografía de nodo y activos de sistema de archivos empaquetados
para paquetes de esquema, conformidad, criptografía y admisión. El paquete
fijado no afirma ser compatible con el navegador ni con el tiempo de ejecución
de Deno.

## Validación y criptografía

`parseStrictJson` y `parseStrictJsonObject` rechazan UTF-8 no válidos, listas de
materiales, miembros de objetos duplicados, entradas numéricas no admitidas y
otras sintaxis fuera de la canalización documentada JSON. `SchemaCatalog` valida
el conjunto de esquemas empaquetado exacto. `canonicalJsonBytes` crea RFC 8785
bytes; La validación exitosa del esquema por sí sola no reemplaza la
canonicalización o la verificación de firma.

`SignedDocumentCodec.sign` selecciona un perfil explícito, valida la hora
protegida, canonicaliza la proyección sin firmar, obtiene una firma estricta
Ed25519 de 64 bytes a través de `SigningKey`, adjunta el sobre y valida el
documento final. `verify` consume UTF-8 bytes sin procesar y ejecuta las etapas
de análisis, esquema, sobre de firma, resolución de clave, canonicalización y
firma en ese orden. El `VerifiedSignedDocument` devuelto expone evidencia
inmutable, copias de bytes defensivas, hashes completos y de firma, tiempo
protegido y la clave resuelta.

La resolución de claves requiere evidencia Organization completa de Registry.
Una clave seleccionada, una entrada de caché o un indicador de confianza
proporcionado por la persona que llama no es una instantánea completa de
Registry.

## Marcos, paquetes y conformidad

`FrameCodec` analiza y codifica valores de fotogramas admitidos, pero no abre un
socket, no autentica una sesión, persiste un cursor, programa trabajo ni aplica
una transición autorizada. Una implementación debe proporcionar esas
responsabilidades de tiempo de ejecución de nivel superior.

`packageRoot` localiza el árbol de artefactos empaquetados buscando su
`PROTOCOL_PIN.json`; localizar ese archivo no valida su contenido ni ningún
resumen de artefactos. `runConformance` ejecuta solo el manifiesto de
conformidad estructural y los vectores a través del catálogo de esquemas
empaquetado. El comando `missionweaveprotocol-conformance` invoca ese mismo
corredor estructural.

El paquete anclado incluye criptografía y activos de admisión para conocer el
origen exacto de la publicación, pero no expone las API públicas que verifican
los resúmenes de criptografía o del paquete de admisión ni ejecutan esos
manifiestos de evaluación. Las aplicaciones no deben tratar `packageRoot` ni un
informe de conformidad estructural exitoso como prueba de que esos dos paquetes
fueron verificados.

## Primera admisión

`AdmissionService` expone la preparación asincrónica, la primera admisión y la
repetición histórica sobre el verificador de documentos firmados sincrónico. La
resolución actual Registry es síncrona; la emisión en contexto confiable puede
ser sincrónica o asincrónica; La búsqueda y la adición de Admission Log son
asincrónicas. Continúe con la [TypeScript Referencia de admisión](../admission/)
para conocer los resultados exactos del adaptador y el orden de llamadas.

## Límites de disponibilidad explícitos

<SupportStatus status="not-implemented" /> **Mission orquestación**: no se
exporta ninguna máquina de estado Mission ni fachada de orquestación de alto
nivel.

<SupportStatus status="not-implemented" /> **Programador Worker**: no se exporta
ninguna cola, programador, ejecutor de concesión ni bucle de recuperación
Worker.

<SupportStatus status="not-implemented" /> **Servicio de puerta de enlace
hospedada**: el paquete proporciona `FrameCodec`, no un servicio de puerta de
enlace hospedada con transporte, sesión, TLS, enrutamiento o propiedad de
contrapresión.

<SupportStatus status="not-implemented" /> **Runtime de persistencia
autoritativa**: no se exporta ningún tiempo de ejecución de persistencia local
respaldado por una base de datos o Agent.

Esas ausencias son parte del contrato de ejecución soportado. Las aplicaciones
no deben inferir capacidades de tiempo de ejecución de referencia Python a
partir de nombres de protocolos compartidos.
