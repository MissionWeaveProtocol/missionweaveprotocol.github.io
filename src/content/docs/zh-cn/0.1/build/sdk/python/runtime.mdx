## 导入模型

`missionweaveprotocol.__init__`
为签署的文件、准入、捆绑验证、预算、租赁和授权提供精心策划的顶级导出。更广泛的参考运行时是公共子模块 API： 进口
`Core` 从 `missionweaveprotocol.core`, `AgentRuntime` 从
`missionweaveprotocol.agent`, `Scheduler` 从
`missionweaveprotocol.scheduler`，以及记录在模块中的其他名称 API 存货。不要假设每个公共子模块类型都是从包根目录重新导出的。

## 核心、商店和交易边界

`Core` 是权威的状态机外观。其公共 `query`、`replay` 和 `perform` 操作由
`AuthoritativeStore`
支持。商店合约暴露了交易、检查和生命周期边界；内存中、SQLite、通用 SQL 和 PostgreSQL 实现不会改变协议的原子性、修订、幂等性或防护要求。

`SQLiteAgentStore`
是 Agent-本地。它存储重播位置、Group 上下文、检查点、调度程序状态、已见事件和挂起的出站操作，以便 Agent 可以恢复。这些投影是可重建的，不能成为 Mission 或 Group 真相的权威。继续使用[持久性和恢复](../../../runtime/persistence-and-recovery/)进行规范分离。

外部数据库是部署依赖项。 `PostgreSQLStore`
需要配置数据库服务和驱动程序；连接可用性或本地缓存命中并不能证明已提交权威转换。

## Agent，调度程序和重放

`AgentRuntime.start_session` 建立单个活动本地会话并返回
`AgentRuntimeSession`。该会话接受 Group 范围的上下文和凭证、准备执行并公开
`Scheduler`。调度程序承认工作，应用转换，调度或抢占，并从快照重建。
`AgentReplay` 和 `EventProjector`
从有序事件恢复本地投影并拒绝间隙或不一致的投影状态。

Execution
Lease、策略、预算和委托 API 是相互独立的检查。在产生副作用之前，已调度的 WorkItem 仍然需要当前 fencing、已接受的工作、适用策略、剩余预算和有效的最小权限授权。

## 验证、信任和框架

在受保护的处理之前，请验证严格的 JSON 和固定的草案 2020-12 架构，保留协议标量字节，规范化签名投影，验证 Ed25519 材料，并从完整的 Registry 证据中解析所选密钥。确切的六阶段顺序在[验证、规范化和签名](../../../runtime/validation-canonicalization-and-signing/)中指定。

`missionweaveprotocol.wire` 拥有类型化框架模型以及
`parse_frame`、`parse_received_frame` 和 `encode_frame`。 `GroupGateway`
将这些帧绑定到会话激活、订阅、游标、重播和核心操作。生产网络部署必须提供安全绑定、身份验证输入、TLS
1.3 证书和密钥、背压限制和操作隔离。 Python 包提供网关运行时；它不提供部署网络权限。

## 一致性和升级

`SchemaCatalog` 和 `run_manifest` 执行支持的本地验证表面。
`verify_cryptography_bundle` 和 `verify_admission_bundle`
将打包的工件绑定到记录的Pin和摘要。 `missionweaveprotocol-conformance`
向操作员公开结构清单运行程序。在检查打包的密码学和准入工件身份时，分别调用两个捆绑验证函数。

每当 SDK 提交、协议 pin、架构集、加密包、准入包或部署适配器发生更改时，请再次运行一致性。传递一个子集仅证明该子集；它不建立数据库持久性、网络安全性、硬件容量或生产准备情况。
